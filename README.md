# FORGE — Autonomous Revenue Recovery Agent

> **Detect. Diagnose. Repair. Verify. Approve. Recover.**

FORGE is an AI-powered incident-repair platform that detects a broken application endpoint, diagnoses the failure, generates a source-code patch, tests the patch inside an isolated **CreateOS Sandbox**, and presents evidence for human approval before applying it to a controlled demo application.

**Hackathon focus:** a genuine end-to-end autonomous code-writing/execution loop, with infrastructure provisioned using **Stripe Projects**. The flagship demonstration repairs a failing e-commerce checkout endpoint and verifies recovery using Stripe test-mode payments. Stripe Projects is distinct from Stripe Payments; the latter is an optional demo integration, not a prerequisite for provisioning.

## The five-minute demo

1. Open the FORGE dashboard and a healthy sample storefront.
2. Click **Inject checkout failure** (demo-only admin action).
3. The checkout health probe returns a 500; an incident is created.
4. Click **Start autonomous repair**; the agent inspects the stack trace and a tightly scoped source snapshot.
5. FORGE generates a patch, uploads the fixture to CreateOS, runs tests, and streams logs to the dashboard.
6. Review the diff, test results, and verification evidence; click **Approve & apply**.
7. The demo checkout recovers and a Stripe test-mode transaction succeeds. Show actual recovery time and audit trail.

**Definition of done:** a real bug, real generated diff, real CreateOS execution, independently authored passing tests, and a recovered endpoint. No fabricated agent traces, test counts, or recovery metrics.

## Tech stack

- **Web:** Next.js App Router, TypeScript, Tailwind CSS, shadcn/ui, Lucide icons, Recharts.
- **Backend:** Next.js route handlers plus a separate Node.js worker for long-running repairs; Zod validation.
- **Agent:** LLM provider behind `LLMProvider` interface; structured JSON output and bounded repair attempts.
- **Execution:** `@nodeops-createos/sandbox` SDK.
- **Persistence:** Neon PostgreSQL, Drizzle ORM.
- **Infrastructure:** Stripe Projects CLI for Neon and Vercel (confirm provider availability via `stripe projects catalog`).
- **Payments (demo):** Stripe Payments test mode only; server-side API and webhook verification where used.
- **Realtime:** server-sent events backed by persisted incident events; polling fallback.
- **Deployment:** Vercel for dashboard/API, durable worker on a Node-capable host (or a local worker for the judged demo).

## Core data model

- `incidents`: id, app_id, title, severity, status, error_signature, created_at, recovered_at.
- `repair_runs`: id, incident_id, attempt, status, sandbox_id, started_at, finished_at.
- `patches`: id, repair_run_id, unified_diff, changed_files, validation_status, approved_by, approved_at.
- `test_results`: id, repair_run_id, suite, passed, failed, exit_code, duration_ms, sanitized_output.
- `incident_events`: id, incident_id, seq, type, payload, created_at.
- `audit_logs`: id, actor, action, target_id, metadata, created_at.

## Status lifecycle

`healthy → detected → diagnosing → patching → testing → awaiting_approval → applying → verifying → recovered`

Failure branches: `repair_failed`, `verification_failed`, `timed_out`, `cancelled`, `rolled_back`. A test pass **never** by itself sets `recovered`.

## Setup

```bash
pnpm install
npm install -g @stripe/cli@latest
stripe plugin install projects
stripe projects init forge
stripe projects catalog
stripe projects add neon/postgres
stripe projects add vercel/project
stripe projects env --pull
```

Run `stripe projects --help` and inspect the provider catalog before provisioning. Add the CreateOS and LLM keys privately, then run migrations and the demo seed scripts according to `package.json` once implemented. These docs are a **build specification**, not a claim that the application has already been implemented.

## Build order and acceptance gates

1. **Provision:** Stripe Projects initializes, provisions Neon, and generates an auditable stack manifest.
2. **Detect:** fixture checkout reliably fails with a real HTTP 500 and incident is persisted.
3. **Repair:** LLM produces a bounded patch against allowed fixture files.
4. **Execute:** CreateOS runs the original failing test, patched tests, and a regression suite.
5. **Approve:** UI shows diff and raw/sanitized evidence before approval.
6. **Recover:** patch is applied to a controlled demo copy, health probe passes, and Stripe test checkout succeeds if configured.
7. **Present:** deployed dashboard, public repository, concise demo recording, and submission details are ready.

**MVP exclusions:** arbitrary GitHub repository access, unsupervised production deploys, real-money transactions, multi-tenant billing, and fully autonomous infrastructure mutation.
